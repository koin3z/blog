# HTML + Tailwind Diagram Generator

技術情報を、編集可能なHTMLと背景透過PNGの組に変換する。
PNGを最終成果物とし、HTMLを再編集できる原本として残す。

## 成果物

- `<name>.html`
  - Tailwindユーティリティで構成した編集可能な原本
  - `#diagram`を固定キャンバスとして持つ
- `<name>.png`
  - `#diagram`だけを撮影した背景透過PNG
- `<name>.report.json`
  - 寸法、アルファ値、はみ出し、最小文字サイズ、外部通信の検査結果

ユーザーが保存先を指定した場合は同じディレクトリに3ファイルを置く。
指定がない場合は、現在の作業に適したGit管理対象外の作業ディレクトリで生成し、確認後にPNGとHTMLの配置先を決める。

## 作業原則

- 図が伝える主張を1文で定義してから配置を決める
- キャンバスをスライドではなく、図の内容を囲む透明な境界として扱う
  - 独立した表紙見出し、キッカー、凡例、ページ番号は、意味上必要な場合だけ置く
  - 空白は接続関係やグループ境界を示すために使い、発表資料らしい「間」を作るために広げない
- 既定は平面的で簡潔な見た目にする
  - グラデーションのない有彩色のベタ面、細い線、控えめな角丸を使う
  - 影、グラデーション、光彩、半透明の装飾面は、依頼で必要な場合だけ使う
- 枠は、システム境界、状態、比較対象、明示的な所属など、境界自体に意味がある場合だけ使う
  - 近接と整列だけで所属を表せる場合は、大きな外箱を追加しない
  - 順序だけを表す場合は、線、小さなノード、直接ラベルをカード列より先に検討する
- 入力資料にない技術的事実や因果関係を補わない
- 白、灰、黒だけで図を完成させず、主要ノード、番号ノード、境界線、ラベル面の少なくとも1種類に有彩色を使う
  - 既定は主色1色と同色相の濃淡2〜3段階にする
  - 分類、段階、状態、責任の違いがある場合、または添付例が複数色を使う場合は、明度と彩度を揃えた2〜4色を使える
  - 白と濃いInkは文字色として使えるが、白・灰・黒を主要カードの基調色にしない
  - 色だけを意味の手掛かりにせず、矢印、位置、番号、形状、ラベルも併用する
- 要素過多を文字縮小だけで解決しない
  - 先に重複説明、装飾、意味のないコンテナを除く
  - 次に線、位置、直接ラベルへ置き換える
  - その後で配置方向とキャンバス寸法を調整する
  - それでも収まらなければ図を分割する
- 外側のキャンバスは透明にし、カード、ラベル、注釈自体には必要な不透明背景を付ける
  - 配置先の明暗が不明な場合は、白と`#0F172A`の両方へPNGを重ねて確認する
  - 直接ラベルがどちらかで読めない場合は、影や文字アウトラインではなく、選択した主色の淡色で文字の背面だけに最小限の不透明な面を置く
- 外部フォント、外部画像、外部アイコンへ依存しない
  - 日本語を含むローカルフォントスタックを使う
  - アイコンは装飾を抑えたインラインSVGを使う

## ワークフロー

### 1. 添付画像を構造化する

構成例の画像が添付されている場合は、HTMLを作る前に画像を表示して次を記録する。

1. 画素寸法とアスペクト比
2. 主な読み順と視線の移動方向
3. 反復するカード、層、列、行の数
4. グリッド、余白、整列基準
5. 矢印、線、包含、対応関係
6. 見出し、本文、注釈の情報階層
7. 背景と各要素の不透明・半透明の使い分け
8. 塗り面と線画の比率、枠が意味上の境界か単なるレイアウト枠か
9. 主色、補助色、淡色面の役割と、色相の違いが意味を持つか
10. 図全体のタイトル、アイコン、影、凡例が存在するか、存在しないか
11. 描画内容の外接矩形と四辺の余白

添付画像は配置と情報階層の参照として扱い、画像そのものをHTMLへ埋め込まない。
画像内の固有の内容や技術的主張は、依頼で再利用を求められていない限り転記しない。
添付画像の四隅が白く見えても、ユーザーが透過を指定した場合は外側を透過にする。

### 2. 内容を設計する

次の順で情報を整理する。

1. 読者が図から読み取る結論
2. ノード、層、選択肢、または時点
3. ノード間の方向、包含、比較、または変化
4. 各ノードに必要な最小限の説明
5. 制約、例外、残る課題

依頼が十分に具体的なら質問せずに進める。
判断によって内容や意味が変わる場合だけ確認する。

### 3. パターンと寸法を選ぶ

[図解パターン](references/patterns.md)から、関係を最も少ない視線移動で読めるパターンを1つ選ぶ。
[デザインシステム](references/design-system.md)で余白、書体、配色、コネクター、内容量の基準を確認する。

寸法は、先にノードと接続を配置し、その外接矩形へ必要な余白を加えて決める。
16:9やスライド寸法を既定にしない。
次の値は完成寸法ではなく、CSS上の論理寸法を設計し始めるための範囲である。
PNGの画素密度が必要な場合は論理寸法を倍にせず、同じHTMLを`--scale 2`で出力する。
論理幅は、ブログ本文など実際の表示幅へ近づける。
予定表示幅へ縮小した後の最小文字サイズも計算し、原則として14px以上を保つ。
たとえば、960pxの図を760pxで表示するとき、HTML上の18pxは約14.3pxになる。

| 用途                       | 寸法の開始範囲     | 外周余白 |
| -------------------------- | ------------------ | -------- |
| 小さな分類、コマンド群     | 480〜840×160〜280  | 16〜28px |
| 3〜5段階の横フロー         | 720〜1000×200〜360 | 20〜36px |
| 4〜7要素のハブ・スポーク   | 800〜1100×520〜760 | 28〜44px |
| 3〜5層のレイヤー、縦フロー | 640〜900×360〜700  | 24〜40px |
| 3〜4列の比較               | 720〜1000×280〜620 | 24〜40px |

ユーザー指定の寸法を優先する。
指定がない場合は、次の順で内容に合わせる。

1. カード、ラベル、コネクターを必要最小限の寸法で配置する
2. 全要素の外接矩形へ上表の外周余白を加える
3. 文字やストロークが切れないことを確認する
4. 上下または左右に用途のない帯状の空白が残る場合はキャンバスを縮める

空白を除いた図の外接矩形が、原則としてキャンバスの幅と高さの70〜94%へ収まるようにする。
ハブ・スポークなど、関係を示す空白自体が必要なパターンでは、全体の透明画素率ではなく最外周ノードの外接矩形で判断する。

### 4. HTMLを生成する

1. [基本テンプレート](assets/base.html)を出力先へコピーする
2. `#diagram`の`data-width`、`data-height`、幅、高さを同じ値へ更新する
3. `role="img"`と、図から読み取れる内容を説明する`aria-label`を設定する
4. `#tailwind-probe`を削除しない
5. TailwindクラスをHTML内にリテラルで記述する
6. コネクターとアイコンはインラインSVGで記述する

次の契約を保つ。

```html
<main
  id="diagram"
  data-width="760"
  data-height="150"
  class="relative h-[150px] w-[760px] overflow-hidden bg-transparent"
  role="img"
  aria-label="図の内容を説明するラベル"
>
  <!-- 図解内容 -->
</main>
```

- `html`、`body`、`#diagram`と`#diagram`の祖先ラッパーに背景色や背景画像を付けない
- 原則として`#diagram`を`body`の直接の子にする
  - ラッパーが必要な場合は背景を透明にし、フィルター、マスク、疑似要素、影、クリッピングを付けない
- `#diagram`の外へ影、矢印、文字を出さない
- アニメーション、ホバー依存、クリック操作を入れない
- 同梱Tailwindの`script`以外のスクリプト、`on*`イベント、`javascript:` URLを入れない
- `canvas`、`iframe`、`object`、`template`、フォーム要素を入れない
- `img`、CSS画像、`data:`画像を使わず、図形はインラインSVGで記述する
- SVGのSMILアニメーションを含めない
- `clip-path`、マスク、CSSフィルター、疑似要素の内容を使わない
- `contain: paint|content|strict`、`content-visibility`、旧式の`clip`を使わない
- `border-image`と`-webkit-box-reflect`を使わない
- SVGマーカーを使わず、矢じりはインラインSVGの図形として直接描く
- CSSのリストマーカーを使わず、箇条書き記号はHTML要素またはインラインSVGで直接描く
- `text-shadow`、CSSアウトライン、`-webkit-text-stroke`を使わない
- `text-decoration`と`text-emphasis`を使わず、線や強調記号は独立した要素で描く
  - 文字の強調には太さや色を、輪郭には要素の境界線を使う
- 影のオフセット、ぼかし、広がりを含む描画範囲をキャンバス内へ収める
- 影を付けた要素またはその祖先を`transform`や`zoom`で変形しない
- `#diagram`の外に、キャンバスと重なる固定要素や兄弟要素を置かない
- 本文と注釈は原則16px以上にし、2行以上の説明を読ませる場合は18px以上にする
- 長い文章をカードへ詰めず、意味を保った短い句へ分解する
- ノードはタイトルと、必要なら1行の短い補足を基本にする
- 図全体の見出し専用領域を既定で作らない
  - 見出しが必要なら、関係図のノードまたはグループラベルとして組み込む
- 主カードは`rounded-xl`または`rounded-2xl`を基準にし、`rounded-3xl`を既定にしない
- 影は既定で使わない
  - 奥行きが意味を持つ場合だけ、境界を曖昧にしない弱い影を1種類使う
- アイコンは役割の識別が速くなる場合だけ置き、全カードへ機械的に付けない

### 5. PNGへ変換する

スキルディレクトリを`<skill-dir>`として次を実行する。

```bash
node <skill-dir>/scripts/render-diagram.cjs \
  --input <output-dir>/<name>.html \
  --output <output-dir>/<name>.png \
  --min-font-size 16 \
  --force
```

高解像度が必要な場合だけ`--scale 2`を追加する。
CSS上の寸法は変えず、PNGの画素数だけ2倍になる。

レンダラーはTailwindのCDNリクエストを同梱版へ差し替え、それ以外の外部・ローカルリソース要求を遮断するため、PNG変換時にネットワークや別ファイルを読み込まない。
Playwrightが見つからない場合は、検査を省略したPNGを作らずにエラーで停止する。
Codex内では同梱ランタイムまたはプロジェクトのPlaywrightを再利用する。
別環境へ持ち出す場合は、PlaywrightとChromium、またはPlaywrightから起動できるシステムChromeを用意する。
ブラウザーの起動前に失敗した場合はレポートも生成されないため、標準エラーのセットアップ案内を確認する。

### 6. 検証して修正する

`<name>.report.json`の`success`が`true`になるまで修正と再変換を繰り返す。

次をすべて確認する。

- PNG寸法が`data-width`×`data-height`×`scale`と一致する
- PNGの四隅のアルファ値が`0`で、透明画素と不透明画素の両方がある
- PNG外周帯の90%以上が完全透過である
- PNG全体の5%以上が完全透過である
- `#diagram`、`html`、`body`と祖先ラッパーに背景色や背景画像がない
- 祖先ラッパーが`#diagram`をクリップせず、描画へ影やフィルターを加えていない
- 1個の子要素がキャンバス面積の90%以上を不透明な背景で覆っていない
- 子要素と文字がキャンバスからはみ出していない
- ボックス影とSVGストロークがキャンバス端で切れていない
- `text-shadow`、CSSアウトライン、`-webkit-text-stroke`を使っていない
- 変形やズームを反映した表示文字が指定した最小文字サイズ以上である
- Tailwind以外の外部通信を要求していない
- `role="img"`と空でない`aria-label`がある

PNGを目視し、次も確認する。

- 最初の3秒で読み順が分かる
- 背景を透過させたスライドに見えず、内容を小さく囲んだ図に見える
- 図全体の見出し、広い上下余白、大きな影がなくても関係を説明できる
- 最外周ノードの外接矩形に対し、キャンバスが不必要に大きくない
- 矢印の方向と接続先が曖昧でない
- 同じ意味の要素が同じ形、余白、書体で表現されている
- 白、灰、黒だけで完成せず、主要な面または線に有彩色が使われている
- 複数色を使う場合、色相の違いが分類、段階、状態、責任、または参照構成と対応している
- 改行位置が日本語の単語や英語の識別子を不自然に分断していない
- 透明背景でもカードや注釈の輪郭を判別できる
- 配置先の明暗が不明な場合、白と`#0F172A`の両方へ重ねても文字、線、境界を判別できる
- 添付例がある場合、列数、読み順、主従関係、余白のリズムが参照構成と一致する

### 7. 引き渡す

PNGを先に示し、HTMLと検査レポートを併記する。
変更可能な内容と、入力資料から保持した技術的前提を短く伝える。

## リファレンスの育成

再利用価値のある良い出力が得られた場合は、固有名詞と案件固有情報を除いたHTMLパターンを`assets/examples/`へ追加する。
追加した作例を[図解パターン](references/patterns.md)から明示的にリンクし、適用条件と避ける条件を記録する。
単に色が違うだけの作例は増やさない。
