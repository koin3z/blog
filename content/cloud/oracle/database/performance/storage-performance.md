## Overview

- ストレージ性能は、IOPS、スループット、レイテンシを組み合わせて評価する
- IOPSとスループットはI/Oサイズ、到達可能なIOPSはレイテンシと同時実行I/O数によって結び付く
- **IOPSだけでは、ストレージやアプリケーションの速さを比較できない**
  - I/Oサイズ、読取り／書込み、ランダム／シーケンシャル、同期条件、キュー深度、測定位置を揃えて比較する

| 指標 | 単位 | 表すもの | 重視する処理 |
| --- | --- | --- | --- |
| IOPS | IOPS | 1秒間に完了したI/O要求数 | 小さいランダムI/O、OLTP、索引参照 |
| スループット | MB/s、MiB/s、GB/s | 1秒間に転送したデータ量 | 全表走査、バックアップ、リストア |
| レイテンシ | μs、ms | 1回のI/Oが完了するまでの時間 | 同期読取り、`COMMIT`時のREDOログ同期書込み |

## IOPSとスループットの関係

同じ測定位置で、対象期間の平均I/Oサイズを用いる場合、IOPSとスループットには次の関係がある。

```text
スループット ≒ IOPS × 平均I/Oサイズ

スループット [MiB/s] ≒ IOPS × I/Oサイズ [KiB] ÷ 1,024
```

- 10,000 IOPSで4 KiBずつ転送すると、約39.1 MiB/sになる
- 1,000 IOPSで256 KiBずつ転送すると、250 MiB/sになる
- 2つ目はIOPSが低いが、1秒間に転送するデータ量は大きい

この式は、アプリケーション、データベース、OS、ブロックデバイス、ストレージサービスのどこで測るかを揃えた概算である。上位層のI/Oはキャッシュに吸収されたり、下位層で分割または結合されたりするため、異なる層のIOPSとI/Oサイズを掛けても一致しない。

### 2つの性能上限

ストレージ製品には、最大IOPSと最大スループットが別々に設定されることがある。同じ条件で両方の最大値へ到達できるとは限らない。

```text
I/Oサイズから見た到達可能なIOPS
  ≤ min(最大IOPS, 最大スループット ÷ I/Oサイズ)
```

> [!EXAMPLE] 仮のストレージ仕様
>
> 最大20,000 IOPS、最大300 MiB/sのストレージを考える。
>
> - 4 KiB I/Oでは、20,000 IOPSに達しても約78.1 MiB/sであり、IOPS上限が先に効く
> - 64 KiB I/Oでは、約4,800 IOPSで300 MiB/sとなり、スループット上限が先に効く
> - 最大値が切り替わるI/Oサイズは、`300 MiB/s ÷ 20,000 IOPS ≒ 15.4 KiB`と概算できる

### 単位

| 表記  | 意味            |
| ----- | --------------- |
| 1 MB  | 1,000,000 bytes |
| 1 MiB | 1,048,576 bytes |
| 1 Mb  | 1,000,000 bits  |

- `B`はbyte、`b`はbitを表し、同じ接頭辞では8倍異なる
- 製品仕様と測定結果を比較するときは、MBとMiB、秒当たりの値と測定間隔当たりの合計を区別する

## レイテンシとキュー深度

**キュー深度（Queue Depth）**は、ある時点で未完了になっているI/O数を表す。定常状態の平均値には、次の関係が成り立つ。

```text
同時実行I/O数 ≒ IOPS × 平均レイテンシ [秒]
IOPS ≒ 同時実行I/O数 ÷ 平均レイテンシ [秒]
```

- 同時実行I/O数が1、平均レイテンシが1 msなら、理論上は約1,000 IOPSになる
- 同じ1 msで32個のI/Oを並列に処理できれば、理論上は約32,000 IOPSになる
- 実際には、ストレージが飽和すると待ち行列によってレイテンシが増え、IOPSは比例して伸びなくなる
- キュー深度を増やして得た最大IOPSは、個々のI/Oが低レイテンシで完了したことを意味しない

### レイテンシの分布

平均レイテンシだけでは、少数の遅いI/Oを把握できない。

- **P50**：50%のI/Oがこの時間以内に完了する
- **P95**：95%のI/Oがこの時間以内に完了する
- **P99**：99%のI/Oがこの時間以内に完了する
- **P99.9**：99.9%のI/Oがこの時間以内に完了する

同期I/OやOLTPでは、平均値と最大IOPSだけでなく、P99やP99.9が応答時間とタイムアウト要件を満たすか確認する。

## 性能を変える条件

| 条件 | 性能への影響 |
| --- | --- |
| I/Oサイズ | 小さいほどIOPS上限、大きいほどスループット上限へ到達しやすい |
| ランダム／シーケンシャル | 物理媒体だけでなく、先読み、キャッシュ、ファイルシステム、ストレージ内部処理の効率が変わる |
| 読取り／書込み比率 | 書込みでは複製、ジャーナリング、キャッシュの書戻し、永続化処理が加わる場合がある |
| 同期／非同期 | 同期I/Oは完了を待つためレイテンシ、非同期I/Oは同時実行数の影響を強く受ける |
| キュー深度とジョブ数 | 大きくすると並列度を引き出せるが、飽和後は待ち時間を増やす |
| ワーキングセット | メモリやストレージキャッシュに収まると、媒体の性能ではなくキャッシュを測る場合がある |
| 実行時間 | 短い測定は立ち上がり、初期キャッシュ、バースト性能へ偏る場合がある |
| ファイルシステム | メタデータ、先読み、ジャーナリング、書戻しが加わる |
| データ内容 | 圧縮や重複排除を行うストレージでは、データの圧縮率や重複率が結果を変える |
| 共有資源 | 同じホスト、ネットワーク、ストレージを使う別ワークロードが結果を変える |

ランダム／シーケンシャル方式だけの影響を比較する場合は、I/Oサイズや並列度を揃える。媒体がSSDかHDDかによって差の大きさは変わり、クラウドストレージではサービス上限とネットワーク経路も加わる。

## 性能を制約する経路

ストレージへのI/Oは複数の層を通り、各層でキャッシュ、分割、結合、待ち行列が発生する。

```mermaid
flowchart LR
  A["アプリケーション"] --> D["Database<br/>データベースバッファキャッシュ"]
  D --> O["OS／ファイルシステム<br/>ページキャッシュ、I/Oドライバ"]
  O --> V["ストレージ接続"]
  V --> H["ホスト／インスタンスの<br/>ストレージ上限"]
  H --> N["ネットワーク"]
  N --> S["ストレージサービス"]
```

```text
到達可能なIOPS
  ≤ min(
       ストレージのIOPS上限,
       ストレージのスループット上限 ÷ 平均I/Oサイズ,
       インスタンスとアタッチメントのIOPS上限,
       インスタンスとネットワークのスループット上限 ÷ 平均I/Oサイズ,
       実際の同時実行I/O数 ÷ 平均レイテンシ
     )
```

- データベースバッファキャッシュやOSページキャッシュへヒットした要求は、下位層へ物理I/Oを発行しない
- 単一ボリュームの性能を上げても、ホストまたはインスタンスの合計ストレージ帯域が先に上限へ達していれば改善しない
- 複数ボリュームへ分散しても、インスタンスまたはホストの合計上限が最小なら合計性能は伸びない
- OS、ファイルシステム、CPU、暗号化、圧縮、データベース処理が先に飽和すれば、数式上の上限へ到達しない
- 性能問題は、アプリケーションからストレージまで同じ時間帯の指標を並べて、最初に飽和または待ちが発生した層を特定する

## データベース処理との対応

| データベース処理 | 主に確認する指標 | 理由 |
| --- | --- | --- |
| OLTP、索引による単一ブロック読取り | IOPS、P99レイテンシ | 多数の小さいランダムI/Oを短時間で完了する必要がある |
| `COMMIT`に伴うREDOログのフラッシュ | 書込みレイテンシ、P99 | フォアグラウンド処理がLGWRによる永続化の完了を待つ |
| 全表走査、パラレル問合せ | 読取りスループット | 大量データをまとめて読み取る |
| RMANバックアップ／リストア | 読取り／書込みスループット | ストレージ、CPU、ネットワーク、保存先を通して大量データを転送する |
| Data Pump | エンドツーエンドのスループット | SQL処理、変換、圧縮、ストレージ、ネットワークのうち最も遅い処理に制約される |
| ソートやハッシュ結合のTEMP退避 | IOPS、スループット、レイテンシ | I/Oサイズとランダム／シーケンシャルの比率が実行計画と並列度で変わる |

- IOPSはトランザクション数ではない
  - 1トランザクションが複数の物理I/Oを発行する場合がある
  - データベースバッファキャッシュへのヒットにより、物理I/Oを発行しない場合もある
- `COMMIT`と物理I/Oは1対1ではない
  - LGWRのスケジューリング、グループコミット、ストレージまでの書込み経路が`COMMIT`待機時間へ影響する
- データベースの論理読取り、OSのブロックデバイス統計、ストレージサービスのIOPSは、測定位置が異なる
- データベース待機イベントの時間にはOS、I/Oキュー、ネットワーク、ストレージの処理が含まれる場合があり、ストレージ装置内だけのレイテンシとは一致しない

## fioによる測定

Doc: [fio documentation](https://fio.readthedocs.io/en/latest/fio_doc.html)

`fio`による1回の測定結果ですべての性能を代表させず、測定目的ごとに条件を変える。

| 測定目的 | 最小構成の例 | 主に読む値 |
| --- | --- | --- |
| 単発の読取り応答 | 4 KiBランダム読取り、`iodepth=1`、`numjobs=1` | `clat`のP50とP99、`lat`の平均 |
| IOPS上限 | 4 KiBまたは実処理相当のランダムI/O、深度を段階的に増加 | IOPS、P99、実際のキュー深度 |
| スループット上限 | 256 KiB以上のシーケンシャルI/O | MiB/s、IOPS、CPU、P99 |
| 実運用相当 | 実際のI/Oサイズ、読取り／書込み比率、同期条件、同時実行数 | IOPS、MiB/s、P99、アプリケーション処理時間 |

- `iodepth`は、1つのジョブが未完了のまま維持しようとするI/O数である
  - `numjobs × iodepth`は全体の最大同時実行数の概算になる
  - 同期I/Oエンジン、OS、アプリケーションの発行動作によって設定値まで到達しないため、`fio`出力の`IO depths`で実際の深度を確認する
- `fio`は、送信処理にかかった`slat`、送信後から完了までの`clat`、両者を合計した`lat`を区別する
  - 既定では`clat`のパーセンタイルを表示する
  - 総レイテンシのパーセンタイルが必要な場合は`lat_percentiles`を有効にする

### 読取り測定例

次の例は、全領域へ事前にデータを書き込んだ専用テストファイルを読取り専用で測定する。スパースファイルや未書込み領域を避け、測定したいキャッシュ層より十分に大きいワーキングセットを用意する。

```bash
fio --name=latency-read \
  --filename=/mnt/fio-test/read-test.dat \
  --direct=1 --rw=randread --bs=4k \
  --ioengine=libaio --iodepth=1 --numjobs=1 \
  --time_based --runtime=120 --ramp_time=30 \
  --group_reporting --readonly
```

IOPS上限を測る場合は、`iodepth`と`numjobs`を段階的に増やし、IOPSの伸びとP99レイテンシの悪化を同時に記録する。スループット上限を測る場合は、実処理に合わせて`rw=read`と大きい`bs`を使用する。

### 測定条件

- `rw`、`bs`、`iodepth`、`numjobs`、`ioengine`、`direct`を記録する
- `runtime`、`ramp_time`、ワーキングセット、テスト領域のサイズを記録する
- テストファイルの作成方法と、全領域へデータを書き込んだかを記録する
- rawデバイスまたはファイル、ファイルシステム、マウントオプション、OS、カーネル、`fio`のバージョンを記録する
- ストレージの容量と性能設定、ホストまたはインスタンスの構成、CPU、接続方式、ボリューム数を記録する
- 平均だけでなくP50、P95、P99、P99.9、実際のI/O深度、CPU使用率を保存する
- ウォームアップ後の定常区間を複数回測定し、最高値だけでなく分布と実行間の差を確認する
- 最大性能テストと、本番ワークロードを再現するテストを分ける

> [!WARNING] 測定対象の保護
>
> 読取り専用の測定でもI/O帯域を占有し、本番処理へ影響する場合があるため、本番環境へ最大負荷をかけない。 `write`、`randwrite`、`randrw`などは、rawデバイスだけでなく通常ファイルの内容も上書きする。書込み測定は、破棄可能な専用のテスト用ボリュームだけで行う。

`direct=1`はOSのページキャッシュを回避するが、デバイスまたはコントローラ内部のキャッシュを無効化せず、電源断後の永続性も保証しない。`fsync`や`fdatasync`を含む測定は永続化待ちを含むファイルI/Oを評価できるが、LGWRやグループコミットを含むOracle Databaseの`COMMIT`経路そのものは再現しない。

## ボトルネックの判定

| 観測結果 | 疑う制約 | 次の確認 |
| --- | --- | --- |
| キュー深度を増やしてもIOPSが横ばいで、P99だけ上昇する | IOPS上限または過剰なキュー | ボリューム上限、スロットリング、性能曲線の折れ曲がりを確認する |
| I/Oサイズを増やすとIOPSが反比例して減り、MiB/sが横ばいになる | スループット上限 | ボリューム、インスタンス、ネットワークの各上限を比較する |
| 複数ボリュームの合計が一定値から伸びない | インスタンスまたはホストの合計上限 | ホストのストレージ上限とネットワーク帯域を確認する |
| テスト領域を大きくすると性能が低下する | キャッシュの影響 | `direct`、ワーキングセット、各層のキャッシュを確認する |
| バッファ経由の書込みは速いが同期時に停止する | 書戻しキャッシュ | 永続化を含む同期書込みで再測定する |
| ストレージのレイテンシは低いがデータベース待機が長い | ストレージ以外の待ち | CPU、ロック、REDOログ、ファイルシステム、I/O発行側を確認する |
| IOPSとスループットに余力がある | アプリケーション側の発行不足または別の制約 | キュー深度、CPU、SQL、並列度を確認する |
