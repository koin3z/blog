## Overview

仮想マシンでは、ゲストOSを実機のように動かしながら、実際のCPU、メモリ、デバイスの制御権をVMM（Virtual Machine Monitor）に残す必要がある。

このページでは、そのための古典的な方式である**trap-and-emulate**を説明する。

焦点は、なぜこの方式が古いx86ではそのまま成立しなかったのかにある。

バイナリトランスレーション、準仮想化、VMX modeの比較は、[[linux/x86_virtualization_approaches|x86におけるプロセッサ仮想化の方式]]で扱う。

## VMMに求められること

Doc: [Popek and Goldberg, Formal Requirements for Virtualizable Third Generation Architectures](https://doi.org/10.1145/361011.361073)

PopekとGoldbergは、仮想化可能なアーキテクチャに求められる性質として、等価性、資源管理、効率性を整理した。

| 条件         | 意味                                                                   |
| ------------ | ---------------------------------------------------------------------- |
| **等価性**   | ゲストで実行したプログラムが、対応する実機での実行と同等に振る舞う。   |
| **資源管理** | VMMがハードウェア資源を制御し、ゲストがVMMの管理外へ直接作用できない。 |
| **効率性**   | 多くの命令は実CPUで直接実行され、VMMの介入を必要な場面へ限る。         |

すべての命令をソフトウェアで模倣すれば資源管理はしやすいが、実行速度が大きく低下する。

逆に、ゲストOSへ実機を自由に操作させれば高速でも、仮想マシン同士やホストを分離できない。

trap-and-emulateは、その二つを両立させるために、通常の処理はCPUへ任せ、問題になる操作だけをVMMへ戻す。

## trap-and-emulateの流れ

Doc: [技術評論社：x86プロセッサにおけるプロセッサ仮想化](https://gihyo.jp/dev/serial/01/vm_work/0004)

ゲストOSをVMMより低い権限で実行すると、権限を必要としない命令は直接実行できる。

一方で、CPUやデバイスの重要な状態を変更する操作では、CPUが例外としてVMMへ制御を渡せる。

このVMMへの制御移動を**trap**と呼ぶ。

VMMは原因となった操作を調べ、ゲストの仮想CPUや仮想デバイスの状態を更新する。

この代替処理を**emulate**と呼ぶ。

```text
ゲストOSが命令を実行する
  ↓
通常の命令なら、実CPUがそのまま実行する
  ↓
捕捉が必要な操作なら、CPUがtrapを発生させる
  ↓
VMMが仮想的な結果を作る（emulate）
  ↓
ゲストOSを再開する
```

たとえばゲストOSが仮想ディスクを操作するとき、VMMは実ディスクを直接操作させる代わりに、ゲストに割り当てた仮想デバイスに対する操作として処理する。

ゲストOSからは命令が成功したように見えるが、実機の資源はVMMの制御下に残る。

## x86の保護機構を使う発想

x86の**プロテクトモード**は、メモリ保護、I/O保護、ソフトウェア間の権限分離を提供する。

その権限分離が、**リングプロテクション**である。

一般的なOSでは、カーネルがring 0、アプリケーションがring 3で動作する。

アプリケーションが特権命令を実行したり、許可されていないメモリやI/Oへアクセスしたりすると、CPUはカーネルへ制御を移す。

この保護機構を仮想化にも使うと、次の配置を考えられる。

```text
実機のring 0 : VMM
実機のring 1またはring 2 : ゲストOS
実機のring 3 : ゲストOS上のアプリケーション
```

この配置では、ゲストOSが特権命令を実行したときに、VMMがtrapを受けて処理できるはずである。

## なぜ古いx86では足りなかったか

trap-and-emulateが機能するには、VMMが制御すべき命令をすべて捕捉できなければならない。

しかし古いx86には、**センシティブ命令**の一部が特権命令ではないという問題があった。

センシティブ命令とは、システムの状態を変更する命令、または現在のシステム状態によって動作が変わる命令である。

そのためVMMは、センシティブ命令を観察し、必要に応じて仮想的な状態へ置き換えられなければならない。

| 問題                           | ゲストOSで起きること                                                       | trap-and-emulateだけでは困る理由                          |
| ------------------------------ | -------------------------------------------------------------------------- | --------------------------------------------------------- |
| 動作が権限に依存する非特権命令 | ゲストOSをring 0から下げると、実機上のring 0とは異なる結果を得る。         | 命令がtrapしなければ、VMMは結果を補正できない。           |
| 実機状態に影響し得る非特権命令 | 例として`POPF`はフラグレジスタを復元し、割り込みに関わる状態へ影響し得る。 | VMMが捕捉できなければ、実機の状態を安全に仮想化できない。 |

ここでの問題は、「資源に直接触れる命令がすべて特権命令ではなかった」ことだけではない。

現在の権限レベルによって結果が変わるだけでも、ゲストOSは実機上の自分と異なる状態を観測し得る。

ゲストOSは本来ring 0で動く前提で作られているため、この差があると正しく動作できない。

> [!NOTE] 説明モデル
>
> trap-and-emulateは「危険な操作が必ず監視者へ通知される」ことを前提にする。
>
> 古いx86の難しさは、監視すべき操作の一部が通知なしに実行できた点にある。

## バイナリトランスレーションによる補完

**バイナリトランスレーション**は、trapできないセンシティブ命令を、実行前にVMMが安全な命令列へ置き換える方法である。

VMMは問題の命令を代替処理に変換し、ゲストが期待する状態を保つ。

この変換はゲストに見えない形で行われるため、OSを改造せずに完全仮想化を実現できる。

ただし、VMMが命令列を解析し、変換後も正しい状態を維持する必要があるため、実装は複雑になる。

この問題意識が、後のIntel VT-xやAMD-Vといったハードウェア仮想化支援につながった。

## 現代のCPU仮想化への接続

Intel VT-xのVMX modeやAMD-VのSVMは、ゲストOSをゲスト内のring 0として動かしつつ、VMMが指定した命令やイベントで制御を取り戻せるようにする。

この制御移動はVM exitと呼ばれる。

そのため、VMMは古いリング圧縮とソフトウェア変換だけに依存せず、CPUの支援を受けてゲストを制御できる。

ただし、VMX modeはtrap-and-emulateの概念そのものを消すものではない。

必要な場面でゲストからVMMへ制御を戻し、VMMが仮想的な結果を作るという基本構造を、CPUがより直接的に支援する仕組みである。
